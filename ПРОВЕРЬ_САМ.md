# Проверить самому за десять минут

Ничего не нужно принимать на слово. Ниже четыре проверки, каждая
выполняется одной командой и показывает результат своими глазами.
Нужен только Docker.

---

## 1. Потрогать проблему руками (две минуты)

Поднять чужой сервер — PostgreSQL с таблицей заказов на 300 000 строк и
PostgREST поверх неё. Нашего кода в нём нет.

```bash
thirdparty/run.sh
```

Теперь обратиться к **одному и тому же адресу** `/orders` четырьмя
разными способами и посмотреть на время:

```bash
for q in "limit=5" "limit=20000" "order=amount.desc&limit=20000" "id=eq.500"; do
  curl -s -o /dev/null -w "%-34s %{time_total} с\n" "http://127.0.0.1:8500/orders?$q"
done
```

Что получается (измерено 20.09.2026):

| запрос | время |
|---|---|
| `/orders?limit=5` | 0,002 с |
| `/orders?id=eq.500` | 0,003 с |
| `/orders?limit=20000` | 0,054 с |
| `/orders?order=amount.desc&limit=20000` | **0,254 с** |

Разница **в 118 раз** на одном адресе. Балансировщик видит только
`/orders` и считает все четыре обращения одинаковыми. Вес задаётся на
маршрут — а различие лежит внутри маршрута, и весами оно недостижимо.

## 2. Увидеть, что это находится само из журнала (одна минута)

Сгенерировать трафик и натравить на журнал диагностику:

```bash
python3 thirdparty/traffic.py
python3 loadlens/loadlens.py thirdparty/logs/access.log
```

Инструмент читает обычный журнал nginx — не код, не трассировку — и
сообщает, что внутри `/orders` разброс 27 раз, что оценка по маршруту
ошибается на 177 % против 34 % по признакам запроса, и что дороже всего
обходится сортировка. Про сортировку ему никто не говорил, он вывел это
из времён ответа.

Добавить `--html отчёт.html` — получится страница, которую можно открыть
в браузере и показать.

## 3. Увидеть, к чему это приводит и что с этим делает маршрутизатор

```bash
docker/run.sh
```

Открыть **http://127.0.0.1:8400**. Идёт поток лёгких запросов, их время
рисуется на графике, пунктир — порог 200 мс.

Что делать на странице:

1. **Нажать «тяжёлый запрос»** в режиме «всё в асинхронный движок».
   На графике появится ступенька: один тяжёлый запрос задержал
   десятки лёгких, которые к нему отношения не имеют.
2. **Переключить на «по числу соединений»** — так работает обычный
   балансировщик — и нажать снова. Ступенька станет меньше, но
   останется.
3. **Переключить на «по оценке стоимости»** и нажать снова.
   Ступеньки почти не будет.
4. **Включить смешанный поток** — пойдёт тот же трафик, на котором
   получены числа в статьях, — и сравнить показатель «медленнее 200 мс»
   в трёх режимах.

Измерено в этих контейнерах: **56 % → 18 % → 4 %**. Без Docker на той же
машине 86 % → 38 % → 7 %: сетевой мост добавляет постоянную задержку.
Порядок сохраняется, абсолютные значения — нет.

## 4. Проверить посылку на чужих производственных данных

Скачать [трассу Azure Functions 2019](https://github.com/Azure/AzurePublicDataset/releases/tag/dataset-functions-2019)
(Microsoft Research, 55 МБ), распаковать и выполнить:

```bash
python3 thirdparty/azure_trace.py function_durations_percentiles.anon.d01.csv \
                                  function_durations_percentiles.anon.d02.csv
```

32 968 настоящих функций клиентов Azure, 1,8 млрд вызовов. У 44,6 % из
них разброс времени внутри одной функции не меньше десятикратного.

Здесь важна и оговорка: **типичная функция расходится в 8 раз, а не в
61.** Числа 61 и 85 с нашего стенда — специально подобранные тяжёлые
операции, и за обычное положение дел мы их не выдаём. В трассе также нет
параметров запросов, поэтому она подтверждает посылку, но не
предсказание.

## Убрать за собой

```bash
docker/run.sh stop
thirdparty/run.sh stop
```

## Если что-то не сходится

Все числа, которые здесь названы, лежат в файлах в `data/` — это правило
проекта: ни одно число не попадает в текст, пока не лежит в файле.
Проверка соответствия статей данным выполняется командой
`python3 tools/verify_numbers.py`.
