# Маршрутизатор на Go

Самостоятельная программа: один двоичный файл без зависимостей. Нужна
двум категориям — тем, у кого nginx не стоит, и тем, кому важно знать,
сколько стоит сама маршрутизация.

```bash
cd gorouter && go build -o loadlens-router .

SYNC_URL=http://127.0.0.1:8201/process \
ASYNC_URL=http://127.0.0.1:8202/process \
MODEL=../data/power_law.json BUDGET_MS=30 \
./loadlens-router
```

| переменная | значение по умолчанию |
|---|---|
| `LISTEN` | `127.0.0.1:8700` |
| `MODEL` | `data/power_law.json` |
| `BUDGET_MS` | `30` |
| `SYNC_URL`, `ASYNC_URL` | адреса движков |

`GET /status` показывает, сколько работы висит на каждом движке, сколько
решений принято и во сколько обходится одно решение.

## Зачем ещё одна реализация

Политика здесь та же, что в `core/policies.py` и в
`nginx/loadlens.lua`. Повторение сделано ради проверки: если бы третья
реализация на другом языке дала другое поведение, значит результат
держался на частности реализации, а не на подходе.

Сквозной замер (`gorouter/benchmark.py`, данные
[../data/gorouter.json](../data/gorouter.json)) — 40 секунд, 24 потока,
тот же смешанный трафик:

| | модуль в nginx | маршрутизатор на Go |
|---|---|---|
| лёгкие, медиана | 11,3 мс | 11,1 мс |
| лёгкие, p95 | 73,0 мс | 74,9 мс |
| доля медленнее 200 мс | 0,0 % | 0,0 % |

Поведение совпало. Пропускная способность у Go в этом замере ниже
(47,4 против 53,4 запросов в секунду), но сравнивать её здесь нельзя:
маршрутизатор работал на хосте, а движки в контейнерах с пробросом
портов, и каждое обращение проходило лишний раз через посредника
Docker. Это разница условий, а не реализаций.

## Сколько стоит само решение

Вопрос «не будет ли распределитель сам грузить сервер» задают первым.

```bash
cd gorouter && go test -bench BenchmarkDecide -benchtime 3s -run '^$' .
```

**58 наносекунд на решение, ноль выделений памяти.** Для сравнения, та
же политика на Python — 1,6 микросекунды.

Под нагрузкой маршрутизатор сообщает другое число: **около 1,2
микросекунды**. Расхождение не ошибка и его стоит понимать. В
изолированном замере решение считается в один поток на прогретом кэше;
под нагрузкой к нему добавляются состязание двадцати четырёх горутин за
счётчики занятости и два обращения к системному таймеру, которыми и
ведётся сам замер. Честная оценка сверху — 1,2 мкс.

Даже по верхней оценке при тысяче запросов в секунду это 1,2
миллисекунды процессорного времени в секунду: **примерно одна десятая
процента одного ядра.**

## Проверки

```bash
cd gorouter
go vet .
go test .          # тяжёлое обращение обязано уходить из цикла событий
```

Проверка политики намеренно устроена так, чтобы не проходить впустую:
она сначала убеждается, что оценка блокировки тяжёлого обращения
действительно превышает бюджет, иначе сравнивать нечего.
