# LoadLens Diagnose

Показывает, чего не видит ваш балансировщик нагрузки.

## Зачем

Балансировщики распределяют запросы по кругу или по числу соединений.
Веса, если они есть, задаются на маршрут. Но стоимость запроса маршрутом
не определяется: `/api/search?limit=10` и `/api/search?limit=5000` идут
по одному адресу и различаются на порядки. Настроить веса так, чтобы это
учесть, нельзя — величина, которую нужно выразить, в модель весов не
помещается.

Инструмент читает журнал обращений и отвечает на три вопроса:

1. насколько стоимость различается **внутри** одного маршрута;
2. объясняется ли разброс параметрами запроса, которые прокси видит до
   обработки, — и если да, то каким и по какому закону;
3. во сколько раз ошибается оценка по маршруту против оценки по
   параметрам.

## Запуск

Зависимостей нет, нужен только Python 3.10 и сам журнал.

```bash
python loadlens.py access.log
python loadlens.py access.log --html report.html
```

Поддерживаются combined-формат nginx с `$request_time`, JSON-строки и
CSV. Формат определяется автоматически. Ничего не ставится в путь
запроса, код сервиса не меняется.

Чтобы nginx писал время ответа, добавьте `$request_time` в формат
журнала:

```nginx
log_format timed '$remote_addr - - [$time_local] "$request" '
                 '$status $body_bytes_sent "$http_referer" '
                 '"$http_user_agent" $request_time';
```

## Демонстрация

```bash
python loadlens.py demo_access.log --html demo_report.html
```

`demo_access.log` — не выдуманный файл: длительности в нём взяты из
фактических замеров нашего стенда и переведены в обычный формат журнала
веб-сервера.

На нём инструмент самостоятельно восстанавливает зависимости
`size^1.91` и `days^1.98` при истинном значении показателя 2,00 — то
есть выводит алгоритмическую сложность операций из одних только времён
ответа.

## Как читать результат

**Разброс внутри маршрута** — отношение 99-го процентиля к медиане. Если
он больше пяти, балансировщик по маршрутам заведомо неточен.

**Объясняет** — доля разброса, которую берёт на себя найденный параметр.
Высокое значение означает, что стоимость запроса предсказуема **до** его
обработки, а значит, ею можно управлять.

**Ошибка оценки** сравнивается на наименее загруженных обращениях. В
журнале рабочей системы измеренное время складывается из собственной
стоимости запроса и ожидания в очереди; ожидание от параметров не
зависит и ни одной оценкой не предсказуемо, поэтому включать его в
сравнение значило бы мерить шум. Очередь способна время только
увеличить, поэтому самые быстрые обращения в каждой группе близких
значений параметра ближе всего к собственной стоимости.

## Чего инструмент не делает

Не измеряет блокировку напрямую: по журналу видно, что запросы
перекрывались во времени, но не видно, обслуживались ли они одним
потоком выполнения. Показатель подверженности блокировке — верхняя
оценка, а не сама блокировка.

Не даёт рекомендаций по конфигурации. Он показывает, есть ли у вас
проблема и насколько она велика; что с ней делать — отдельный разговор.
