# LoadLens

**Балансировщики нагрузки не знают, сколько стоит запрос, который они
распределяют. Мы научились это предсказывать.**

Балансировщик раздаёт запросы по кругу или по числу соединений. Веса,
если они есть, задаются на маршрут. Но стоимость запроса маршрутом не
определяется:

| обращение | время выполнения |
|---|---|
| `/api/search?limit=10` | **10 мс** |
| `/api/search?limit=600` | **640 мс** |

Один адрес, разница в 61 раз. Вес задаётся на маршрут, а различие лежит
внутри маршрута — настроить веса так, чтобы это учесть, невозможно в
принципе.

Из-за этого редкие тяжёлые запросы задерживают множество лёгких. На
асинхронных движках (Node.js, Python asyncio, FastAPI) один
вычислительный запрос останавливает обработку **всех** остальных:
измерено, что то же обращение задерживает соседей на 9 мс в потоковом
сервере и на 125 мс в цикле событий.

## Попробовать за минуту

Весь стенд поднимается одной командой, кроме Docker ничего не нужно:

```bash
docker/run.sh            # затем открыть http://127.0.0.1:8400
```

Откроется живая демонстрация: поток лёгких запросов, переключение
режимов маршрутизации и впрыск тяжёлого запроса. Подробности и честная
оговорка о том, почему числа в контейнерах слабее, — в
[docker/README.md](docker/README.md).

## Диагностика на своих данных

Диагностика читает обычный журнал обращений и показывает проблему на
ваших данных. Ничего не ставится в путь запроса, код сервиса не
меняется, зависимостей нет.

```bash
python loadlens/loadlens.py loadlens/demo_access.log --html report.html
```

На демонстрационном журнале инструмент сам, ничего не зная об устройстве
сервиса, восстанавливает алгоритмическую сложность операций из одних
только времён ответа:

| маршрут | найденный закон | истинный показатель |
|---|---|---|
| `/api/image/thumbnail` | ~ size^**1,91** | 2,00 |
| `/api/report/generate` | ~ days^**1,98** | 2,00 |

Подробности и поддерживаемые форматы журналов — в
[loadlens/README.md](loadlens/README.md).

## Что входит в продукт

**1. Диагностика** (`loadlens/`) — читает журнал nginx, JSON или CSV и
отвечает: насколько стоимость различается внутри каждого маршрута, чем
разброс объясняется, во сколько раз ошибается оценка по маршруту.
Работает на любом стеке, потому что читает журнал, а не код.

**2. Маршрутизатор** (`gateway.py`, `core/`) — шлюз, который оценивает
нагрузку каждого запроса и раскладывает обращения по обработчикам,
подходящим для них физически.

## Чем это подтверждено

Всё измерено на стенде с настоящей нагрузкой — хеширование, кодирование
изображений, обращения к СУБД и по сети, ни одного `sleep` вместо
работы. Замеры воспроизводятся одной командой.

| Утверждение | Измерено |
|---|---|
| Движки расходятся в блокировке, а не в скорости | 9 мс против 125 мс |
| Стоимость не определяется маршрутом | разброс до 85 раз внутри адреса |
| Стоимость предсказуема по видимым признакам | 80 % ошибки → 3,4 % |
| Маршрутизация лучше любого одиночного движка | +18…46 % пропускной способности |
| Доля подтормаживающих лёгких запросов | 89 % → 7 % |

## Проверено не только на своём стенде

Собственный стенд уязвим для возражения: его писали мы, и он мог быть
устроен так, чтобы подтвердить нашу мысль. Поэтому проверка сделана
дважды на чужом.

**На чужой программе** — PostgREST поверх PostgreSQL с таблицей на
300 000 строк, нашего кода в пути запроса нет. Разброс стоимости внутри
одного маршрута **в 27 раз**, ошибка оценки по маршруту 177 % против
34 % по признакам запроса. Инструмент сам, из одного журнала, нашёл, что
дороже всего там сортировка — примерно в 11 раз. Разбор:
[thirdparty/RESULT.md](thirdparty/RESULT.md).

Эта проверка нашла и слабость инструмента: один параметр объяснял разброс
лишь на 18 % против 78–99 % на нашем стенде, потому что у настоящего
интерфейса стоимость определяют несколько вещей сразу. Оценка переделана
на несколько признаков, ошибка на отложенной половине упала с 57,7 % до
38,6 %.

**На производственной трассе Microsoft** — Azure Functions 2019,
**32 968 функций, 1,8 млрд вызовов**. У половины функций p99 превышает
медиану в 8 раз, у 44,6 % разброс не меньше десятикратного. Это
подтверждает посылку проекта на настоящей эксплуатации, но не
предсказание: параметров запросов в трассе нет. Разбор:
[thirdparty/AZURE.md](thirdparty/AZURE.md).

Типичный обработчик расходится в 8 раз, а не в 61. Числа 61 и 85 раз с
нашего стенда — специально подобранные тяжёлые операции, и выдавать их
за обычное положение дел мы не будем.

## Где это не работает

Границы определены и измерены, а не замолчаны.

- **На однородном потоке маршрутизация вредна**, а не бесполезна: при
  обращениях только к вводу-выводу она проигрывает асинхронному движку
  43 %.
- **Против least-connections это размен, а не победа:** −20 %
  пропускной способности за шестикратное снижение доли подтормаживающих
  запросов.
- **При деградации самого охраняемого движка преимущество теряется.**
  Подход опирается на то, что движок остаётся таким, каким его измерили.
- Все замеры сделаны на одной машине, каждый движок в одном процессе.
  Поведение на боевом трафике настоящей компании не проверено.

## Откуда это взялось

Продукт вырос из исследовательской работы, а не наоборот. Научная часть

включая отрицательные результаты и методические ошибки, которые были
допущены и исправлены, — в [PROJECT_STATE.md](PROJECT_STATE.md).

## Структура

| путь | содержимое |
|---|---|
| `loadlens/` | диагностика — продукт, с которого начинается внедрение |
| `gateway.py`, `core/` | маршрутизатор и оценки нагрузки |
| `workers/` | синхронный и асинхронный движки, внешний сервис |
| `experiments/` | профилирование, обучение, замеры, графики |
| `data/`, `figures/` | результаты замеров и рисунки |
| `docs/` | статьи для конференций |
| `ledentsov/` | материалы к премии Леденцова: заявка и презентация |
| `tools/` | сборка статей и оценка объёма |

## Как воспроизвести замеры

```bash
python -m venv venv && source venv/bin/activate
pip install -r requirements.txt

python workers/stub_service.py &     # внешний сервис, порт 8100
python workers/sync_worker.py &      # синхронный движок, 8201
python workers/async_worker.py &     # асинхронный движок, 8202

python experiments/profile_costs.py         # блокировка по сетке параметров
python experiments/collect_cost_samples.py  # замеры для настройки оценок
python experiments/train_cost_model.py      # настройка и проверка оценок
python experiments/benchmark_budget.py      # достижимая граница
python experiments/plot_results.py          # графики
```

Порядок обязателен: профилирование задаёт эталон, сбор замеров даёт
обучающую выборку, и только после этого оценки доступны политикам.
