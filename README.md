# Адаптивная маршрутизация между синхронным и асинхронным веб-движками

Экспериментальный стенд к вопросу: **стоит ли распределять HTTP-запросы
между синхронным и асинхронным движком по оценке нагрузки каждого
запроса, и где в этой задаче действительно нужно машинное обучение.**

Результаты ниже получены измерением на этом стенде. Числа, которых нет в
`data/`, в тексте не приводятся.

## Почему движки вообще есть смысл разделять

Асинхронный движок — один event loop. Пока запрос ждёт ответа внешнего
сервиса, обслуживаются другие: на ожидании он феноменально эффективен.
Но вычисление выполняется в том же потоке неделимо и на всё своё время
останавливает обработку **всех** остальных запросов.

Синхронный движок даёт поток на запрос. Вычисление в одном потоке не
останавливает остальные: планировщик переключает их каждые несколько
миллисекунд, а операции на C (хеширование, кодек JPEG, SQLite)
освобождают GIL и выполняются по-настоящему параллельно.

Измерено (`experiments/profile_costs.py`) — собственное время обработки и
задержка, которую запрос причиняет лёгким обращениям, идущим на тот же
движок:

| запрос | синхронный: своё / блокировка | асинхронный: своё / блокировка |
|---|---|---|
| `/api/auth/verify` | 128 / **9 мс** | 124 / **123 мс** |
| `/api/report?days=75` | 938 / **272 мс** | 922 / **626 мс** |
| `/api/feed?limit=400` | 495 / 10 мс | 492 / 9 мс |

Собственное время от движка почти не зависит. Расходятся движки в том,
сколько вреда запрос причиняет соседям.

## Почему маршрут не отвечает на вопрос «тяжёлый ли это запрос»

Стоимость определяется параметром запроса, а не его адресом:

| запрос | полное время | из них вычисления |
|---|---|---|
| `/api/search?limit=10` | 10 мс | 4 мс |
| `/api/search?limit=600` | 658 мс | 405 мс |
| `/api/report?days=8` | 13 мс | 6 мс |
| `/api/report?days=75` | 926 мс | 616 мс |

Разброс внутри одного маршрута — 65–70 раз. Поэтому таблица
«маршрут → стоимость», на которой работают балансировщики с весами,
заведомо неверна для отдельного запроса, а экспертное правило,
привязанное к маршруту, вынуждено отправить весь маршрут в одну сторону.

## Оценка стоимости по признакам запроса

Все оценки настроены на одних и тех же 384 замерах и проверены на 156
отложенных, где значения параметра в обучении не встречались. Медианная
относительная ошибка:

| оценка | ошибка |
|---|---|
| среднее по маршруту | 80.3 % |
| экспертное правило «пропорционально параметру» | 11.2 % |
| степенной закон, показатель выведен из данных | 3.7 % |
| нейронная сеть | 3.4 % |

Выученные показатели степени против истинных: **1.87–1.95 против 2.00**
для маршрутов с квадратичной сложностью и 0.93–1.02 против 1.00 для
линейных. Показатель модели не сообщался — он выведен из времён ответа.

## Результат: маршрутизация против одиночного движка

Конкурентность 32, смешанный поток, 3 повтора на точку. Приведены
режимы, которых никто не превосходит сразу по обеим осям:

| режим | запросов/с | лёгких запросов дольше 200 мс |
|---|---|---|
| весь трафик в асинхронный движок | 24.7 | 89.3 % |
| весь трафик в синхронный движок | 27.2 | 35.1 % |
| классификатор, порог 15 мс | 29.6–31.1 | 0.4–3.1 % |
| классификатор, порог 30 мс | 31.4–35.1 | 5.0–6.9 % |
| least-connections | 44.1 | 44.4 % |

**Любой режим с классификатором строго лучше обоих одиночных движков
сразу по двум осям.** Например, при пороге 30 мс: +42 % пропускной
способности против «всё асинхронно» и в 13 раз меньше пострадавших
лёгких запросов; +29 % и в 5 раз против «всё синхронно».

Против least-connections это **размен, а не победа**: −20 % пропускной
способности за шестикратное снижение доли пострадавших лёгких запросов.

## Главный вывод: где именно нужно обучение

Оценка нагрузки применяется в двух ролях. Чтобы выяснить, какая из них
определяет результат, роли разведены по разным источникам оценки и
проверены все четыре сочетания (5 повторов по 600 запросов):

| допуск в event loop | вес очереди | запросов/с | лёгкие p95 | лёгких дольше 200 мс |
|---|---|---|---|---|
| правило | правило | 37.6 | 310 мс | 6.4 % |
| правило | **модель** | 36.2 | **137 мс** | **1.7 %** |
| модель | правило | 36.7 | 417 мс | 7.2 % |
| модель | **модель** | 35.5 | **130 мс** | **2.2 %** |

Результат разделяется строго по второму столбцу. Чем принято решение о
допуске — не влияет.

Объяснение, которое этим и проверено:

- **Допуск** («безопасен ли запрос для event loop») требует лишь верного
  **порядка** запросов относительно порога. Любое монотонное по
  параметру правило справляется, и рукописное работает не хуже
  обученного.
- **Взвешивание очереди** требует верной **абсолютной величины** в
  миллисекундах: значения складываются между собой и сравниваются между
  движками. Здесь 11-процентная ошибка правила, систематическая на
  маршрутах с квадратичной сложностью, стоит втрое большей доли
  пострадавших запросов и хвоста в 2.7 раза длиннее.

Ответ на вопрос о практической целесообразности, таким образом, — не
«обучение помогает», а **где именно оно необходимо, а где достаточно
нескольких строк кода**.

## Что в этом стенде настоящее

- Нагрузка — реальные операции: PBKDF2, кодирование JPEG, сортировка,
  чтение SQLite, HTTP-обращение к отдельному сервису. Ни одного `sleep`
  вместо работы.
- Вычисления в асинхронном движке выполняются прямо в event loop, без
  выноса в executor. Это не недосмотр, а исследуемый режим отказа.
- Целевая величина обучения — измеренная секундомером задержка, а не
  придуманная метка класса.
- Значения параметров в трафике непрерывны и не привязаны к сетке
  профилирования: оценка обязана обобщать на не встречавшиеся значения.

## Ограничения, которые нельзя забывать

- Каждый движок — один процесс, то есть около одного ядра из
  шестнадцати. Так устроен CPython, и в проде масштабируют числом
  процессов; это умножает ёмкость, но не меняет описанного эффекта
  внутри процесса.
- Разброс пропускной способности между прогонами достигает ±6 запросов
  в секунду. Выводы делаются по нескольким повторам, хвостовые
  показатели устойчивее среднего.
- Таблица прямого профилирования **не является** верхней границей
  достижимого: она снята при одном сопутствующем запросе, а под полной
  смешанной нагрузкой движок ведёт себя иначе. В замерах она на
  Парето-границу не попала.
- Все замеры на одной машине (WSL2), диск и сеть общие.

## Как воспроизвести

```bash
python -m venv venv && source venv/bin/activate
pip install -r requirements.txt

python workers/stub_service.py &     # внешний сервис, порт 8100
python workers/sync_worker.py &      # синхронный движок, 8201
python workers/async_worker.py &     # асинхронный движок, 8202

python experiments/profile_costs.py         # блокировка по сетке параметров
python experiments/collect_cost_samples.py  # замеры для настройки оценок
python experiments/train_cost_model.py      # настройка и проверка оценок
python experiments/classifier_quality.py    # качество классификатора без нагрузки
python experiments/benchmark_budget.py      # кривая компромисса
python experiments/benchmark_equal_share.py # сравнение при равной ёмкости
python experiments/plot_results.py          # графики
```

Остановить всё:
`ps aux | grep -E "[w]orkers/|[g]ateway.py" | awk '{print $2}' | xargs -r kill -9`

## Структура

| путь | назначение |
|---|---|
| `core/workload.py` | эндпоинты и настоящие операции нагрузки |
| `core/cost_model.py` | оценки стоимости запроса, не требующие обучения |
| `core/predictor.py` | обучаемые оценки: степенной закон и нейронная сеть |
| `core/policies.py` | политики маршрутизации с единым правилом выбора |
| `core/queue_state.py` | взвешивание очередей движков |
| `gateway.py` | шлюз, принимающий решение по каждому запросу |
| `workers/` | синхронный и асинхронный движки, внешний сервис |
| `experiments/` | профилирование, обучение, замеры, графики |
| `PROJECT_STATE.md` | полное состояние работы, включая отрицательные результаты |

Подробный разбор, в том числе методических ошибок, которые были
допущены и исправлены по ходу, — в [PROJECT_STATE.md](PROJECT_STATE.md).
