# Adaptive Routing — адаптивная маршрутизация между Flask и FastAPI

Прототип и экспериментальный стенд для проверки гипотезы: **даёт ли адаптивная маршрутизация HTTP-запросов между синхронным (Flask) и асинхронным (FastAPI) движками, основанная на обученном классификаторе, прирост пропускной способности и снижение задержки по сравнению с использованием одного движка?**

Коротко о результате: гипотеза **подтвердилась** на реалистичном смешанном потоке запросов (одновременно CPU-bound и I/O-bound) — адаптивный шлюз даёт **+39–87% пропускной способности** относительно лучшего одиночного движка и снижает среднюю задержку в 1,8–2,4 раза, причём выигрыш растёт вместе с конкурентной нагрузкой. Причина физически объяснима: у FastAPI один event loop, и CPU-bound запрос, обработанный напрямую в async-хендлере, полностью останавливает обработку всех остальных запросов на время вычисления; Flask таких лок-апов не создаёт (каждый запрос — свой OS-поток), но не умеет дёшево масштабировать большое число конкурентных I/O-ожиданий. Адаптивная маршрутизация обходит обе слабые стороны, направляя каждый запрос на движок, который физически справляется с его типом нагрузки быстрее.

Важная деталь методологии — этому результату предшествовал контрольный эксперимент, который **не подтвердил** гипотезу (раздел [Контрольный эксперимент](#контрольный-эксперимент-и-почему-он-не-мог-получиться)): в нём оба бэкенда эмулировали нагрузку идентичным `sleep(0.1)`, из-за чего у маршрутизации физически не было причины давать выигрыш — она могла только добавлять накладные расходы шлюза. Диагностика этой причины и стала основанием для пересмотра дизайна эксперимента.

## Архитектура

```
                 ┌──────────────────┐
  клиент  ─────► │  Gateway :9000   │
                 │  (FastAPI +      │
                 │   AdaptiveRouter)│
                 └────────┬─────────┘
                          │  load, io_intensity, cpu_usage
                          │  → PyTorch classifier → P(FastAPI)
              ┌───────────┴────────────┐
              ▼                        ▼
      ┌───────────────┐        ┌───────────────┐
      │  Flask :5000  │        │ FastAPI :8000 │
      │ (sync, threads│        │ (async, event │
      │  на CPU-bound)│        │ loop на I/O)  │
      └───────────────┘        └───────────────┘
```

Три независимых процесса: два backend-сервиса и шлюз, который на основе трёх признаков запроса (`load`, `io_intensity`, `cpu_usage`) через обученный классификатор решает, к какому backend'у направить конкретный запрос, и логирует каждое решение. Ключевое отличие от наивной версии — сами backend'ы физически по-разному обрабатывают I/O-bound и CPU-bound запросы (см. `workload.py`), поэтому у выбора движка есть реальная цена ошибки.

## Установка

Требуется Python 3.12+, Linux/WSL2 (тестировалось на Ubuntu 24.04 под WSL2).

```bash
git clone https://github.com/winlast/adaptive-routing.git
cd adaptive-routing

python -m venv venv
source venv/bin/activate

pip install -r requirements.txt
```

Для нагрузочного тестирования дополнительно нужен независимый инструмент [`hey`](https://github.com/rakyll/hey) (используется контрольным скриптом `benchmark.py`; основной эксперимент `benchmark_realistic.py` использует собственный генератор на `httpx` и `hey` не требует):

```bash
sudo apt install hey
# либо: go install github.com/rakyll/hey@latest && export PATH=$PATH:~/go/bin
```

## Быстрый старт

Модель уже обучена и её веса лежат в `data/` — обучать заново не нужно для простого запуска.

```bash
OMP_NUM_THREADS=1 MKL_NUM_THREADS=1 python main.py
```

> Переменные `OMP_NUM_THREADS=1 MKL_NUM_THREADS=1` обязательны — без них PyTorch создаёт избыточный пул фоновых потоков, который вызывает голодание event loop’а шлюза под нагрузкой.

В другом терминале:

```bash
# I/O-bound запрос (io_intensity >= 0.15) — маршрутизируется на FastAPI
curl -X POST http://127.0.0.1:9000/route \
  -H "Content-Type: application/json" \
  -d '{"load": 30, "io_intensity": 0.4, "cpu_usage": 15}'

# CPU-bound запрос (io_intensity < 0.15) — маршрутизируется на Flask
curl -X POST http://127.0.0.1:9000/route \
  -H "Content-Type: application/json" \
  -d '{"load": 120, "io_intensity": 0.05, "cpu_usage": 90}'
```

Переменные окружения для управления режимом работы:

| Переменная | Значения | По умолчанию | Назначение |
|---|---|---|---|
| `ROUTER_MODE` | `neural` \| `heuristic` | `neural` | какой алгоритм принимает решение |
| `AB_TEST_ENABLED` | `true` \| `false` | `false` | включить A/B-разбиение между режимами |
| `AB_TEST_HEURISTIC_SHARE` | 0.0–1.0 | `0.5` | доля трафика на эвристику при A/B |

## Результаты

Поток запросов: 70% I/O-bound (`io_intensity=0.4`, эмулируется `asyncio.sleep`/`time.sleep` ~60–120 мс) + 30% CPU-bound (`cpu_usage=90`, эмулируется настоящим busy-loop ~280 мс), запросы обоих типов идут **одновременно и вперемешку** на один и тот же сервис (не последовательными фазами).

| Конкурентность | adaptive, RPS | Flask-only, RPS | FastAPI-only, RPS | Δ к лучшему одиночному |
|---|---|---|---|---|
| 20 | 44,75 | 32,15 | 12,43 | +39,2% |
| 50 | 56,18 | 31,25 | 11,16 | +79,8% |
| 100 | 58,47 | 31,30 | 11,70 | +86,8% |

Средняя задержка адаптивного шлюза ниже, чем у Flask-only, в 1,8–2,4 раза (323/590 мс при concurrency=20, 636/1535 мс при 50, 1273/3095 мс при 100) и ниже, чем у FastAPI-only, в 2,7–6,1 раза. FastAPI-only при concurrency=100 дополнительно теряет часть запросов по таймауту (14 из 1500) — событие, которого нет ни у Flask-only, ни у adaptive.

Механизм эффекта: у FastAPI один event loop на процесс. CPU-bound busy-loop, выполненный напрямую в async-хендлере (без вынесения в executor — намеренно реалистичный сценарий, в который легко попасть на практике), останавливает обработку **всех** остальных запросов на время вычисления, включая те I/O-bound запросы, которые сами по себе обработались бы почти мгновенно. У Flask такого катастрофического отказа нет (каждый запрос — свой OS-поток, GIL переключается между ними каждые ~5 мс), но пул потоков дороже держать под большим числом конкурентных I/O-ожиданий, чем event loop. Адаптивная маршрутизация ограждает FastAPI от CPU-bound трафика и одновременно не грузит Flask I/O-bound трафиком, забирая для каждого типа запроса движок, которому он физически дешевле обходится.

Точность классификатора (по физически обоснованному правилу `io_intensity >= 0.15` — см. `workload.py`) — 99,7% на отложенной выборке; матрица ошибок — `figures/confusion_matrix.png`.

Полные данные — `data/benchmark_realistic_results.csv`, `data/hypothesis_realistic_throughput.csv`. График — `figures/benchmark_realistic_comparison.png`.

## Контрольный эксперимент и почему он не мог получиться

Первая версия прототипа (сохранена в `data/benchmark_results.csv`, `figures/benchmark_comparison.png`) эмулировала нагрузку в обоих backend'ах идентичным `sleep(0.1)` независимо от типа запроса. При такой постановке между Flask и FastAPI физически нет разницы в скорости обработки одного и того же запроса — соответственно, у маршрутизации не может быть выигрыша, только фиксированные накладные расходы шлюза (лишний сетевой переход + однопоточное принятие решения). Результат контрольного эксперимента (adaptive медленнее лучшего одиночного движка на 5–56%) — прямое следствие этого, а не ошибка классификатора или архитектуры маршрутизации.

Этот результат стал основанием для пересмотра дизайна: чтобы у адаптивной маршрутизации в принципе была возможность выиграть, движки должны реально отличаться по тому, как быстро/безопасно они обрабатывают разные типы запросов — что и реализовано в `workload.py` (I/O-bound vs CPU-bound) и проверено в основном эксперименте.

## API

Gateway (`http://localhost:9000`):

| Метод | Путь | Описание |
|---|---|---|
| `POST` | `/route` | Принимает `{load, io_intensity, cpu_usage, ...}`, возвращает ответ backend'а + метаданные маршрутизации |
| `GET` | `/stats` | Агрегированная статистика по принятым решениям |
| `GET` | `/config` | Текущая конфигурация (режим, A/B) |

Backend'ы (`:5000`, `:8000`): `POST /process`, `GET /health`.

## Известные ограничения

- Flask/FastAPI backend работают на dev-серверах (Werkzeug, `uvicorn` без production-воркеров) — абсолютные цифры throughput не отражают production-производительность, только относительное сравнение архитектур при равных условиях.
- Gateway использует один процесс для принятия решения — это же однопоточное узкое место объясняет, почему p95/p99-задержка adaptive выше, чем у Flask-only (хотя throughput и средняя задержка у adaptive лучше): решения по всем конкурентным запросам сериализуются на одном ядре. Вынесение принятия решения в пул потоков/процессов — очевидное направление дальнейшей работы.
- Датасет для обучения — синтетический, порог `io_intensity >= 0.15` задан вручную, не выведен из реального трафика.
- Эксперимент проводился на одной машине (WSL2, 16 ядер) — сетевой оверхед не отделён от локальной конкуренции за CPU.
- Соотношение I/O-bound/CPU-bound трафика (70/30) и параметры длительности задач (`workload.py`) — тоже заданы вручную; чувствительность результата к этим параметрам отдельно не исследована.
