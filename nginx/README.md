# Модуль для nginx

Отдельный шлюз удобен для исследования, но ставить его в путь запроса
перед боевым сервисом мало кто захочет: это ещё одно звено, которое надо
разворачивать, обновлять и объяснять службе эксплуатации. Здесь та же
политика живёт там, где балансировщик уже стоит — внутри nginx, — и не
добавляет ни одного сетевого перехода.

```bash
nginx/run.sh          # поднять движки и nginx с модулем
nginx/run.sh stop     # убрать
```

| адрес | что делает |
|---|---|
| `POST /route` | маршрутизация по оценке стоимости запроса |
| `POST /baseline` | обычная балансировка `least_conn` — для сравнения |
| `GET /status` | сколько работы висит на каждом движке |

## Что нужно, чтобы поставить это у себя

Три файла и ни одной пересборки nginx:

1. `loadlens.lua` — сам модуль;
2. `power_law.json` — оценка стоимости, полученная из журнала;
3. несколько строк в `nginx.conf`.

Нужен OpenResty или nginx с модулем Lua. Образ не модифицируется:
файлы монтируются внутрь.

Выбор узла сделан через переменную в `proxy_pass`, а не через
`balancer_by_lua`, намеренно. Balancer принимает адрес узла только
числом — доменные имена он не разрешает, и пришлось бы тащить в
конфигурацию разрешение имён с его кэшем и сроками жизни. Переменная
опирается на обычные `upstream`-блоки, а с ними работает весь привычный
набор nginx: проверки живости, keepalive, таймауты.

## Замер

Сравнение устроено так, чтобы различался ровно один фактор: один и тот
же процесс nginx, те же движки, тот же трафик и те же параметры
запросов. Отличается только способ выбора узла.

40 секунд, 24 одновременных потока, смешанный трафик — тот же, на
котором получены числа в статьях. Числа: [../data/nginx_module.json](../data/nginx_module.json).

| | `least_conn` | модуль |
|---|---|---|
| лёгкие запросы, медиана | 103,9 мс | **11,3 мс** |
| лёгкие запросы, p95 | 852,4 мс | **73,0 мс** |
| доля медленнее 200 мс | 36,9 % | **0,0 %** |
| пропускная способность | 67,7 rps | 53,4 rps |

**Это размен, а не чистая победа.** Пропускная способность падает на
21 %: тяжёлые запросы отправляются в потоковый движок, где они идут
медленнее, чем могли бы в цикле событий. Взамен исчезает ожидание
лёгких запросов за чужой тяжёлой работой. Выгодно это там, где важен
отклик, и невыгодно там, где важна только суммарная пропускная
способность.

Ноль медленных запросов — не преувеличение, а следствие устройства: при
бюджете 30 мс тяжёлые обращения в цикл событий не попадают вовсе, и
лёгким не за кем стоять. При другом пороге и другом составе трафика
результат будет другим, порог задаёт положение на кривой размена.

## Как воспроизвести

```bash
nginx/run.sh
python nginx/benchmark.py --seconds 40
nginx/run.sh stop
```
