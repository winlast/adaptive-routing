## Кратко: к чему пришли

Три утверждения, каждое подтверждено измерением с повторами.

1. **Маршрутизация между синхронным и асинхронным движком по оценке
   нагрузки каждого запроса строго лучше любого одиночного движка** —
   одновременно по пропускной способности и по хвосту задержек. Против
   «всё асинхронно»: +42 % запросов в секунду и в 13 раз меньше
   пострадавших лёгких запросов.
2. **Стоимость запроса не определяется его маршрутом.** Разброс внутри
   одного адреса — 65-70 раз. Оценка по маршруту, на которой работают
   промышленные балансировщики с весами, ошибается на 80 %; оценка по
   признакам запроса — на 3.4 %.
3. **Обучение необходимо ровно в одной из двух ролей оценки.** Решение
   «пускать ли запрос в event loop» рукописное правило принимает не хуже
   модели. Взвешивание очереди требует верной абсолютной величины, и там
   ошибка правила стоит втрое большей доли пострадавших запросов.
   Проверено перекрёстным экспериментом на всех четырёх сочетаниях.

## Что представляет собой проект сейчас

Шлюз (`gateway.py`) принимает HTTP-запросы и по каждому решает, в какой
движок его отдать. Движков два (`workers/`): синхронный на потоках
(Flask, порт 8201) и асинхронный на event loop (FastAPI, 8202). Отдельно
поднимается внешний сервис (8100), к которому движки обращаются при
операциях ввода-вывода, — благодаря ему I/O в эксперименте настоящее.

Нагрузка настоящая (`core/workload.py`): PBKDF2, кодирование JPEG,
сортировка, чтение SQLite, HTTP-обращение наружу. Ни одного `sleep`
вместо работы. Шесть маршрутов; **стоимость запроса определяется его
параметром** (`limit`, `size`, `days`), а не адресом.

Все содержательные политики (`core/policies.py`) устроены одинаково и
различаются единственным — источником оценки нагрузки
(`core/cost_model.py`, `core/predictor.py`). Это сделано намеренно: так
измеряется вклад именно оценки, не смешанный с различиями в правиле
выбора.

# Часть 1. История: первая постановка и почему она отброшена

Этот раздел сохранён, чтобы не пройти тот же путь заново.

Исходно стоимость запроса определялась только его маршрутом: шесть
адресов, у каждого фиксированная цена. В такой постановке таблица
«маршрут → стоимость» точна по построению, и задача сводится к
арифметике из теории очередей с точным формульным решением. Выучивать
нечего, поэтому обучение неизбежно проигрывало простой арифметике.

Что было измерено тогда и осталось верным:

- Без конкуренции движки почти неразличимы (разница 1-3 %). Вся разница
  рождается под нагрузкой, из очередей и блокировок.
- Блокировка event loop измерена прямо: лёгкий запрос деградировал с
  25 мс до 1643 мс, когда в асинхронный движок попадала вычислительная
  задача.
- Учёт веса очереди (вместо счёта запросов штуками) поднимал
  балансировщик с 70 до 78 запросов в секунду.
- Обучаемая модель значимого преимущества перед простой балансировкой
  **не показывала**.

Методические ошибки, допущенные тогда и исправленные:

- Обучающие данные собирались случайной политикой, а модель работала в
  состояниях, которые создаёт сама. Смещение распределения устранено
  переходом к сбору с частичным исследованием (`ExploringPolicy`), а
  затем задача вовсе перестроена вокруг профилирования.
- Эксперимент с изменением условий замедлял общую внешнюю зависимость,
  отчего дорожали все движки одинаково и приспосабливаться было не к
  чему. Заменён на асимметричное ухудшение одного движка.
- Первая версия классификатора была математически тождественна правилу
  `if io_intensity >= 0.15`: два из трёх входных признаков на решение не
  влияли вовсе. Это и стало причиной полной переделки.

# Часть 2. Текущая постановка и её результаты

## Диагноз первой постановки

Задача была слишком простой для машинного обучения. Шесть маршрутов с
фиксированной стоимостью каждый — это задача из теории очередей с точным
формульным решением. Выучивать нечего, поэтому арифметика по таблице
неизбежно побеждала, а модель лишь приближала то же самое с шумом. Это
было следствием искусственного упрощения, а не свойством задачи.

## Что изменено

**Стоимость запроса определяется его параметром, а не маршрутом.** Клиент
передаёт `limit`, `size` или `days`; прокси видит это значение в строке
запроса, не заглядывая в бизнес-логику. Замеренный разброс внутри одного
маршрута:

| запрос | полное время | из них CPU |
|---|---|---|
| `/api/search?limit=10` | 10 мс | 4 мс |
| `/api/search?limit=600` | 658 мс | 405 мс |
| `/api/report?days=8` | 13 мс | 6 мс |
| `/api/report?days=75` | 926 мс | 616 мс |

Разброс 65-70 раз внутри одного маршрута. Следствия:

- любая таблица «маршрут → стоимость» заведомо неверна для отдельного
  запроса;
- оптимальный движок меняется внутри маршрута: `search?limit=10` это
  лёгкий I/O (место в асинхронном движке), `search?limit=600` это 405 мс
  вычислений, которые в event loop блокируют всех соседей;
- экспертное правило по маршруту физически не может развести эти случаи.

Показатели степени различаются по маршрутам: для выборок из базы
зависимость линейная, для обработки изображения и агрегации за период —
квадратичная. Поэтому правило «умножить на параметр», которое инженер
пишет руками, верно не везде.

Значения параметра в трафике непрерывны (логравномерное распределение со
смещением к малым значениям), а не выбираются из известного списка:
оценка стоимости обязана обобщать на не встречавшиеся значения.

## Измеренная асимметрия движков (профилирование)

Для каждой пары «запрос, движок» измеряются две величины: собственное
время выполнения и суммарная задержка, причинённая лёгким обращениям,
которые шли на тот же движок параллельно.

| запрос | sync своё / ущерб | async своё / ущерб |
|---|---|---|
| `/api/auth/verify` | 129 / **18** | 123 / **121** |
| `/api/report?days=75` | 938 / **296** | 945 / **683** |
| `/api/image?size=2200` | 249 / 215 | 241 / 238 |
| `/api/feed?limit=400` | 493 / 17 | 491 / 46 |

Собственное время почти не зависит от движка. Расходятся движки в том,
сколько вреда запрос причиняет соседям: в потоковом сервере операции,
освобождающие GIL (хеширование, кодек JPEG, SQLite), выполняются
параллельно с обработкой других запросов, в event loop — нет.

Величина, которую имеет смысл складывать по очереди, — **занятость**
(собственное время + причинённая задержка), а не собственное время.

## Две разные величины о запросе, которые нельзя смешивать

Профилирование измеряет для каждой пары «запрос, движок» собственное
время выполнения и задержку, причинённую лёгким обращениям, которые шли
на тот же движок параллельно. Первая версия меры ущерба брала **сумму**
задержек — это оказалось методической ошибкой. Сумма измеряет потерю
пропускной способности, и по ней движки почти не различаются: в
потоковом сервере планировщик переключает потоки каждые несколько
миллисекунд, поэтому общее отобранное время примерно то же. Различие
движков — в **блокировке**: в потоке лёгкий запрос продвигается
порциями и завершается быстро, в event loop он ждёт чужое вычисление
целиком. Поэтому мера ущерба заменена на наибольшую задержку одного
обращения.

После замены картина стала физически осмысленной (мс):

| запрос | sync своё / блок | async своё / блок |
|---|---|---|
| `/api/auth/verify` | 128 / **9** | 124 / **123** |
| `/api/report?days=75` | 938 / **272** | 922 / **626** |
| `/api/report?days=45` | 325 / 81 | 323 / 212 |
| `/api/feed?limit=400` | 495 / 10 | 492 / 9 |
| `/api/search?limit=600` | 667 / 384 | 633 / 412 |

Собственное время от движка почти не зависит. Блокировка зависит сильно
там, где вычисление освобождает GIL (хеширование, кодек, SQLite), и
слабо там, где оно выполняется чистым Python-кодом (сортировка в
`/api/search`).

Отсюда две величины у каждой оценки стоимости: `cost` — полная цена
запроса, `blocking` — время, на которое движок недоступен остальным.
Очередь взвешивается блокировкой: ожидание внешнего сервиса на 500 мс
движок не занимает и веса в очереди почти не имеет.

## Точность оценки стоимости (главный численный результат)

Все оценки настроены на одной выборке из 384 замеров со значениями
параметра из рабочего распределения; проверка на 156 отложенных замерах
с не встречавшимися значениями. Медианная относительная ошибка:

| оценка | цена запроса | блокировка |
|---|---|---|
| среднее по маршруту | 80.3 % | 53.6 % |
| линейная поправка (показатель = 1) | 11.2 % | 35.0 % |
| степенной закон (показатель выучен) | 3.7 % | 11.1 % |
| нейронная сеть | 3.4 % | 12.6 % |

Разбивка по маршрутам показывает, где именно выигрывает обучение:
`/api/image/thumbnail` — 261 % / 55 % / 3.4 %, `/api/report/generate` —
251 % / 58 % / 7.0 %. Это маршруты с квадратичной зависимостью, для
которых экспертное правило «пропорционально параметру» неверно.
Контрольный случай `/api/auth/verify` (стоимость от параметра не
зависит) даёт 1.3 % у всех оценок — методика измеряет то, что задумано.

Выученные показатели степени против истинных: 1.87-1.95 против 2.00 для
квадратичных маршрутов, 0.93-1.02 против 1.00 для линейных. Показатель
модели не сообщался, он выведен из времён ответа.

## Схема эксперимента

Главный замер построен вокруг вопроса, который соответствует названию
работы буквально: **классификатор решает, безопасен ли запрос для event
loop**. Политика допускает запрос в асинхронный движок, только если
предсказанная блокировка не превышает порога; синхронный движок
принимает всё. Среди допустимых движков выбирается менее занятый.

Порог — не настроечная константа, а параметр компромисса: при нуле весь
трафик уходит в синхронный движок, при бесконечности политика
вырождается в балансировку по весу очереди. Набор порогов даёт кривую
«пропускная способность против хвоста задержек лёгких запросов», и
сравниваются кривые целиком, а не отдельные точки — это снимает произвол
в выборе рабочей точки.

Различаются политики единственным — источником оценки блокировки
(среднее по маршруту, линейная поправка, степенной закон, нейронная
сеть, точная таблица профилирования как верхняя граница).

Для отсчёта в замер включены `all_sync`, `all_async` (маршрутизации нет)
и `least_conn` (балансировка, не различающая запросы).

## Качество классификатора без шума нагрузки (`classifier_quality.py`)

Нагрузочный замер даёт итог, но его разброс между прогонами велик. Тот
же вопрос задан напрямую: разыгрывается 40 000 запросов из рабочего
распределения, для каждого известна истинная блокировка event loop (из
таблицы профилирования), и классификатор с данным порогом решает,
пускать ли запрос в асинхронный движок.

**При фиксированном пороге** — избыточная блокировка, попавшая в event
loop сверх порога, мс на тысячу запросов:

| порог | среднее по маршруту | линейная поправка | степенной закон | нейронная сеть |
|---|---|---|---|---|
| 15 мс | 0 (но 8.2 % зря отклонено) | 46 | 394 | 397 |
| 30 мс | 0 (но 19.6 % зря отклонено) | 27 | 33 | 35 |
| 60 мс | **7520** | 522 | **21** | **21** |
| 120 мс | 9480 | 3674 | 513 | 505 |
| 250 мс | 3246 | 2680 | 59 | **14** |

**При равной доле трафика в асинхронном движке** (пороги подобраны так,
чтобы пропускная способность выравнялась по построению):

| доля | классификатор | блокировки, мс/1000 | самая тяжёлая пропущенная |
|---|---|---|---|
| 60 % | среднее по маршруту | 7340 | **421 мс** |
| 60 % | линейная поправка | 4745 | 11 мс |
| 60 % | обученная модель | 4749 | 18 мс |
| 70 % | среднее по маршруту | 13630 | **426 мс** |
| 70 % | линейная поправка | 6548 | 26 мс |
| 70 % | обученная модель | 6578 | 27 мс |
| 80 % | среднее по маршруту | 20054 | **622 мс** |
| 80 % | обученная модель | 10244 | 74 мс |

Решающий переход — от оценки по маршруту к оценке по запросу: вдвое
меньше блокировок при той же пропускной способности и в 8-16 раз
меньше самый тяжёлый прорвавшийся запрос. Именно он и создаёт хвост.

## Нагрузочный замер: Парето-граница (`benchmark_budget.py`)

Конкурентность 32, 500 запросов, 3 повтора на точку. Приведены режимы,
которых никто не превосходит сразу по обеим осям:

| режим | rps | лёгкие дольше 200 мс |
|---|---|---|
| весь трафик в асинхронный движок | 24.7 | 89.3 % |
| весь трафик в синхронный движок | 27.2 | 35.1 % |
| оценка по маршруту, порог 15 мс | 29.6 | 0.4 % |
| нейронная сеть, порог 15 мс | 31.1 | 3.1 % |
| нейронная сеть, порог 30 мс | 31.4 | 5.0 % |
| степенной закон, порог 30 мс | 35.1 | 6.9 % |
| линейная поправка, порог 60 мс | 38.7 | 14.4 % |
| least-connections | 44.1 | 44.4 % |

Два вывода:

1. **Любой режим с классификатором строго лучше обоих одиночных
   движков сразу по двум осям.** Степенной закон при пороге 30 мс:
   +42 % пропускной способности против «всё асинхронно» и в 13 раз
   меньше пострадавших лёгких запросов; +29 % и в 5 раз против «всё
   синхронно». Это прямое подтверждение гипотезы из названия работы.
2. **Оценка по запросу вытесняет оценку по маршруту почти отовсюду.**
   Из шести режимов «по маршруту» на границе остался один, самый
   консервативный. Остальные вытеснены: степенной закон при пороге
   30 мс даёт 35.1 rps при 6.9 %, оценка по маршруту в той же области —
   31.8 rps при 9.2 %, хуже по обеим осям.

Против least-connections — размен, а не победа: −20 % пропускной
способности за шестикратное снижение доли пострадавших лёгких запросов.
Так и следует написать, не выдавая это за чистый выигрыш.

Таблица прямого профилирования на Парето-границу не попала вовсе.
Называть её «верхней границей достижимого», как было в первой редакции,
неверно: она измеряет блокировку при одном сопутствующем запросе, а под
полной смешанной нагрузкой движок ведёт себя иначе. Формулировки в коде
исправлены.

## Сравнение при равной доле трафика (`benchmark_equal_share.py`)

Сравнивать классификаторы при одном пороге некорректно: порог означает
для разных оценок разное, и сравниваются разные рабочие режимы, а не
точность. Пороги подобраны так, чтобы доля трафика в асинхронном движке
была одинаковой.

Доля 70 %, 3 повтора по 500 запросов:

| классификатор | порог | rps | лёгкие p95 | лёгкие >200 мс |
|---|---|---|---|---|
| среднее по маршруту | 58 | 26.7 | 112 | 2.5 % |
| линейная поправка | 20 | 30.5 | 354 | 6.7 % |
| степенной закон | 15 | 29.9 | 182 | 4.6 % |
| нейронная сеть | 15 | **32.0** | **145** | **3.1 %** |

Перепроверка, 5 повторов по 600 запросов:

| классификатор | rps | лёгкие p95 | лёгкие >200 мс |
|---|---|---|---|
| линейная поправка | 33.7 ±6.2 | 415 | 7.5 % |
| степенной закон | 34.9 ±6.2 | 377 | 5.5 % |
| нейронная сеть | 35.4 ±5.7 | **158** | **2.6 %** |

Два независимых прогона дали одно направление и близкую величину:
обученная модель снижает хвост в 2.5 раза и долю пострадавших запросов
втрое при равной пропускной способности. Разброс по rps велик (±6), но
хвостовые показатели устойчивы.

## Противоречие между офлайн- и нагрузочным измерением, и его разрешение

Офлайн-анализ состава пропущенной в event loop работы при доле 70 %
показывает, что три оценки по запросу **неразличимы**:

| классификатор | сумма, мс/1000 | p90 | p99 | доля >50 мс |
|---|---|---|---|---|
| среднее по маршруту | 13630 | 28.4 | 251.9 | 4.78 % |
| линейная поправка | 6548 | 15.2 | 23.6 | 0 % |
| степенной закон | 6579 | 15.2 | 24.3 | 0 % |
| нейронная сеть | 6578 | 15.2 | 24.2 | 0 % |

То есть различие в нагрузочном замере возникает **не на допуске**.

Рабочая гипотеза: оценка применяется в двух ролях с разными
требованиями. Для допуска достаточно правильного **порядка** запросов
относительно порога — линейное правило монотонно по параметру и порядок
сохраняет. Для взвешивания очереди нужна верная **абсолютная величина**:
значения складываются между собой и сравниваются между движками, а
линейное правило ошибается на 11 % и систематически — на маршрутах с
квадратичной сложностью.

## Проверка механизма: где именно нужно обучение (ГЛАВНЫЙ ВЫВОД)

Две роли разведены по разным источникам оценки
(`split_<допуск>_<вес>_<порог>`), проверены все четыре комбинации.
5 повторов по 600 запросов, конкурентность 32:

| допуск | вес очереди | rps | лёгкие p95 | лёгкие >200 мс |
|---|---|---|---|---|
| линейное правило | линейное правило | 37.6 ±4.5 | 310 | 6.4 % |
| линейное правило | **модель** | 36.2 ±4.7 | **137** | **1.7 %** |
| модель | линейное правило | 36.7 ±4.9 | 417 | 7.2 % |
| модель | **модель** | 35.5 ±5.9 | **130** | **2.2 %** |

Результат разделяется строго по столбцу «вес очереди». Чем принято
решение о допуске, не влияет: 310 против 417 и 137 против 130 —
разнонаправленно и в пределах разброса. Всё определяет источник оценки,
которой взвешена очередь.

**Вывод, который и составляет содержание работы.** Оценка нагрузки
запроса используется в двух ролях, и требования к ней в них разные:

- Решение «безопасен ли запрос для event loop» требует только верного
  **порядка** запросов относительно порога. Любое монотонное по
  параметру правило справляется; рукописное работает не хуже обученного.
- Взвешивание очереди требует верной **абсолютной величины** в
  миллисекундах: значения складываются между собой и сравниваются между
  движками. Здесь 11-процентная ошибка линейного правила,
  систематическая на маршрутах с квадратичной сложностью, стоит втрое
  большей доли пострадавших лёгких запросов (6.8 % против 1.95 %) и
  хвоста в 2.7 раза длиннее.

То есть ответ на вопрос о практической целесообразности — не
«обучение помогает», а **где именно оно необходимо, а где достаточно
нескольких строк кода**.

## Как разрешился заявленный риск

Перед началом было записано: усложнение задачи не гарантирует победу
обучаемой модели, сильный конкурент — рукописное линейное правило, и
если модель его не обойдёт, это следует написать прямо.

Разрешилось так. В маршрутизации как таковой (решение о допуске) модель
рукописное правило **не обходит** — и это записано выше без смягчений.
Обходит она его во второй роли, при взвешивании очереди, и величина
эффекта втрое по доле пострадавших запросов. Обе половины результата
зафиксированы.

## Зависимость выигрыша от уровня нагрузки (`benchmark_load_levels.py`)

Разнородный поток, 400 запросов, 3 повтора на точку. Выигрыш считается
относительно **лучшего** одиночного движка, которым во всех точках
оказался синхронный.

| Конкурентность | Синхронный | Асинхронный | Классификатор | Δ к лучшему | Средняя задержка |
|---|---|---|---|---|---|
| 16 | 32,7 | 26,8 | 43,9 | +34,3 % | в 1,51 раза |
| 32 | 27,8 | 26,1 | 38,3 | +37,8 % | в 1,50 раза |
| 64 | 26,4 | 26,1 | 38,4 | +45,5 % | в 1,69 раза |
| 96 | 27,6 | 25,4 | 32,7 | +18,3 % | в 1,45 раза |
| 128 | 25,5 | 24,8 | 32,3 | +26,4 % | в 1,57 раза |

Итог: **+18…+46 % и в 1,3–1,7 раза**, максимум при конкурентности 64.
Дальше система насыщается по процессорному времени (два движка, два
ядра), и преимущество убывает, оставаясь положительным.

**Числа аннотации не воспроизводятся**, и это записано в статье прямо.
Заявленные 39–87 % и 1,8–2,4 раза получены на предварительной серии,
где вычисление моделировалось холостым циклом: он не освобождает GIL и
парализует асинхронный движок полностью. Контроль на чисто
вычислительном потоке воспроизводит тот режим — асинхронный движок там
выдаёт 8,7 запроса в секунду против 25–27 при настоящих операциях. В
статье это подано как самостоятельный методологический результат:
**эмуляция вычислительной нагрузки холостым циклом завышает оценку
эффекта примерно вдвое.** Такой ход согласован с автором работы.

## Контроль на однородном потоке (утверждение аннотации проверено)

Конкурентность 32, 3 повтора.

| Поток | Лучший одиночный | Классификатор | Балансировка |
|---|---|---|---|
| только ввод-вывод | асинхронный, 231,8 | 122–132 (−43…−47 %) | 166,5 (−28 %) |
| только вычисления | синхронный, 55,9 | 48,8 (−13 %) | 39,7 (−29 %) |

Аннотация утверждает «на однородной нагрузке выигрыша нет» —
подтверждено в усиленной форме: маршрутизация там не бесполезна, а
**вредна**. На вычислительном потоке классификатор проигрывает заметно
меньше балансировки, поскольку верно отказывается пускать вычисления в
цикл событий.

## Изменение условий во время работы: граница применимости (отрицательный результат)

Проверялось, сохраняет ли классификатор преимущество, когда система
меняется после профилирования. В асинхронном движке запускается фоновая
нагрузка, отбирающая у него процессорное время (шумный сосед). Замер
`experiments/benchmark_drift.py`, конкурентность 32, 3 повтора,
300 запросов до ухудшения и 500 после.

| политика | rps до | лёгкие >200 мс до | rps после | лёгкие >200 мс после |
|---|---|---|---|---|
| оценки неизменны | 37.6 | 5.4 % | 35.3 | **86.8 %** |
| поправка по разности с очередью | 40.9 | 6.4 % | 30.0 | 65.8 % |
| состояние движка, сравнение по блокировке | 42.1 | 9.4 % | 28.5 | 61.5 % |
| состояние движка, сравнение по полной цене | 40.8 | 9.7 % | 26.0 | 50.5 % |
| least-connections | 44.7 | 46.6 % | 31.6 | **35.6 %** |

**Вывод отрицательный и его нельзя смягчать.** До ухудшения
классификатор даёт 5.4 % против 46.6 % у least-connections — преимущество
в 8.6 раза, что независимо подтверждает основной результат ещё на одном
прогоне. После ухудшения лучший из адаптивных вариантов даёт 50.5 % при
26.0 rps, тогда как least-connections — 35.6 % при 31.6 rps, то есть
**лучше сразу по обеим осям**. Заранее зафиксированный критерий («не
хуже least-connections») не выполнен ни одним вариантом.

Улучшение сигнала адаптации монотонно улучшает хвост
(86.8 → 65.8 → 61.5 → 50.5 %), но каждая ступень стоит пропускной
способности (35.3 → 30.0 → 28.5 → 26.0) и разрыв не закрывает.

Причина физическая. Ценность классификатора в том, что он не пускает
блокирующую работу в **исправный** event loop. Когда сам event loop
лишён процессорного времени, на нём страдают и запросы, которые ничего
не блокируют, а классификатор продолжает их туда пускать — их блокировка
по-прежнему мала, и формально они безопасны. Правильная реакция — вовсе
перестать пользоваться испорченным движком, и least-connections делает
это самопроизвольно, через рост очереди.

Отсюда формулировка границы применимости для статьи: **подход опирается
на то, что охраняемый движок остаётся таким, каким его измерили.
Изменение нагрузки на соседние ресурсы он переносит, потерю
процессорного времени самим асинхронным движком — нет.** Возможное
продолжение (не проверено, и выдавать за результат нельзя): сочетать
классификатор с балансировкой по загрузке так, чтобы длина очереди
перекрывала решение классификатора при деградации движка.

### Три ошибки постановки этого эксперимента

Каждая давала отрицательный результат, который говорил об эксперименте,
а не о методе. Записаны, чтобы не повторить в четвёртый раз.

1. Замедлялась общая внешняя зависимость — дорожали оба движка
   одинаково, относительный порядок не менялся, приспосабливаться было
   не к чему.
2. Ухудшался синхронный движок. Но политика опирается на оценку
   блокировки **асинхронного**, и от этого она не устаревает.
3. Поправка считала собственную стоимость как «замер минус оценка
   очереди». Под нагрузкой эта разность вбирает ожидание, не связанное с
   деградацией, и раздувалась одинаково у обоих движков (до x9.4 у
   движка, который не менялся). Заменено на нижний дециль отношения
   замера к ожидаемому собственному времени: у исправного движка около
   единицы, у испорченного — 2.36 против 1.06 у соседнего.

# Часть 3.5. Премия Леденцова: что сделано

`research-v2` влит в `ledentsov`. Устаревшая схема архитектуры и её
генератор удалены — они изображали правило `load > 50`, которого в
проекте нет. Конференционные материалы не тронуты.

## Стратегия: вход через диагностику, а не через прокси

Ключевое решение. Никто не поставит незнакомый прокси в путь боевых
запросов, поэтому продавать маршрутизатор «с порога» нельзя. Входом
служит **диагностика**: инструмент читает журнал обращений, ничего не
меняя, и показывает клиенту проблему на его собственных данных. Сначала
человек видит, что его балансировщик слеп, и только потом ему нужен наш
маршрутизатор.

Это не новый продукт, а второй результат исследования («стоимость не
определяется маршрутом, но предсказуема по параметрам»), завёрнутый так,
чтобы посторонний мог проверить его у себя за минуту.

## LoadLens Diagnose (`ledentsov/loadlens/`)

Один файл, **без зависимостей**, читает combined-формат nginx, JSON и
CSV. Отвечает на три вопроса: разброс стоимости внутри маршрута; чем он
объясняется; во сколько раз ошибается оценка по маршруту.

**Решённая методическая проблема.** В журнале рабочей системы измеренное
время включает ожидание в очереди, которое от параметров не зависит и
глушит сигнал: сначала параметр объяснял лишь 29–51 %. Исправлено
подгонкой по нижней огибающей — очередь способна время только
увеличить, поэтому самые быстрые обращения в каждой группе близких
значений параметра ближе всего к собственной стоимости. Стало 78–99 %.

**Проверка на демонстрационном журнале** (снят с нашего стенда,
длительности настоящие): инструмент самостоятельно восстановил
показатели степени 1,91 и 1,98 при истинном значении 2,00, то есть вывел
квадратичную сложность операций из одних времён ответа в логе nginx.

| файл | назначение |
|---|---|
| `loadlens/loadlens.py` | инструмент, 604 строки, stdlib |
| `loadlens/make_demo_log.py` | сборка журнала из замеров шлюза |
| `loadlens/demo_access.log` | 1200 обращений с настоящими длительностями |
| `loadlens/demo_report.html` | готовый отчёт |
| `loadlens/README.md` | краткое руководство |

## Линия статьи, подтверждённая измерениями

1. Разделение трафика между двумя движками даёт выигрыш сразу по двум
   осям относительно любого одиночного движка — это подтверждение
   заявленной гипотезы.
2. Оценка нагрузки по маршруту структурно недостаточна, потому что
   стоимость определяется параметром запроса; нужна оценка по запросу.
3. Обучение необходимо не для решения о маршруте, а для взвешивания
   очередей. Это и есть ответ о практической целесообразности.

4. Граница применимости: преимущество сохраняется, пока охраняемый
   движок остаётся таким, каким его измерили. При потере им
   процессорного времени обычная балансировка по загрузке становится
   предпочтительнее — отрицательный результат, который должен быть в
   статье.

Против least-connections результат — **размен, а не победа**: −20 %
пропускной способности за шестикратное снижение доли пострадавших лёгких
запросов. Писать именно так.

python experiments/benchmark_equal_share.py # сравнение при равной ёмкости

TRAFFIC=mixed LEVELS=16,32,64,96,128 python experiments/benchmark_load_levels.py
TRAFFIC=io_only LEVELS=32 python experiments/benchmark_load_levels.py
TRAFFIC=cpu_only LEVELS=32 python experiments/benchmark_load_levels.py
python experiments/plot_results.py          # графики

Порядок обязателен: профилирование задаёт эталон, сбор замеров —
обучающую выборку, и только потом оценки становятся доступны политикам.

Погасить всё:
`ps aux | grep -E "[w]orkers/|[g]ateway.py" | awk '{print $2}' | xargs -r kill -9`

## Ограничения, которые нельзя забывать и нельзя замалчивать

- Каждый движок — один процесс, то есть около одного ядра из
  шестнадцати. Так устроен CPython; в проде масштабируют числом
  процессов, что умножает ёмкость, но не меняет эффекта внутри процесса.
- Разброс пропускной способности между прогонами достигает ±6 запросов
  в секунду. Выводы — только по нескольким повторам; хвостовые
  показатели устойчивее среднего.
- Таблица прямого профилирования **не является** верхней границей
  достижимого: она снята при одном сопутствующем запросе, а под полной
  смешанной нагрузкой движок ведёт себя иначе. В замерах она на
  Парето-границу не попала. Называть её границей — ошибка, которая уже
  была допущена и исправлена.
- Все замеры на одной машине (WSL2), диск и сеть общие.
- Где обучение должно было бы стать необходимым, но не проверено: когда
  стоимость зависит не от одного известного параметра, а от нескольких
  признаков запроса с взаимодействиями или от категориальных значений.
  Это направление для продолжения, а не доказанный результат.
