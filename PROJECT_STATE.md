## Что представляет собой проект сейчас

Шлюз принимает HTTP-запросы и выбирает, какому воркеру их отдать.
Воркеры (`workers/`): синхронный на потоках, асинхронный на event loop,
пул процессов. Нагрузка настоящая (`core/workload.py`): PBKDF2, сжатие
изображений, сортировка, SQLite, HTTP к отдельному stub-сервису — никаких
`sleep`. Шесть эндпоинтов с разными профилями.

Политики маршрутизации (`core/policies.py`): random, round-robin,
least-connections, least-expected-work, статическое правило, оракул,
обучаемая модель и гибрид.

## Ключевые результаты (проверены, с повторами и оценкой разброса)

1. **Без конкуренции воркеры почти неразличимы** (разница 1–3%). Вся
   разница рождается только под нагрузкой — из очередей и блокировок.

2. **Чистая обучаемая политика значимо проигрывает least-connections**:
   58.6 против 71.8 rps при конкурентности 16, 56.8 против 67.5 при 32.

3. **Причина установлена по данным**: модель отправляла 0% трафика на
   async-воркер, оставляя его простаивать, потому что для отдельного
   запроса он выглядит медленнее. Минимизация латентности запроса теряет
   пропускную способность системы.

4. **Гибрид (балансировка отсекает перегруженных, модель выбирает из
   оставшихся) сравнялся по пропускной способности и значимо улучшил
   SLO**: 17.8% нарушений против 22.9%, бутстреп-ДИ разницы
   [-9.4; -0.7] п.п. Улучшение p95 (-94 мс) незначимо, ДИ пересекает ноль.

5. **Статическое экспертное правило — худшее из всего** (-18% и -25% к
   least-connections). Маршрутизация по типу запроса без учёта загрузки
   вредна.

Итоговая формулировка: знание характера запроса не даёт выигрыша в
пропускной способности сверх простой балансировки по загрузке, но
встроенное в балансировку предсказание значимо снижает долю нарушений SLO.

## Эксперимент с изменением условий (выполнен, результат отрицательный)

Проверялось, даёт ли адаптивность преимущество, когда условия меняются:
в середине прогона внешний сервис замедлялся втрое.

| политика | до: avg / SLO | после: avg / SLO |
|---|---|---|
| least_conn | 246 / 9.4% | 337 / 16.1% |
| least_work | 260 / 7.4% | 351 / 27.0% |
| online_model | 251 / 7.4% | 365 / 22.9% |
| adaptive_work | 245 / 7.0% | 439 / 37.7% |

Адаптивные политики проиграли, least_conn выиграл. **Причина — ошибка в
постановке, а не свойство политик**: замедлялся внешний сервис, общий для
всех трёх воркеров, поэтому все подорожали одинаково и относительный
порядок между ними не изменился. Адаптироваться было не к чему, а
обновление оценок только добавляло шум.

**Следующий шаг: асимметричная деградация.** Нужно ухудшить один воркер
относительно других — например, сократить пул процессов с 4 до 1 через
семафор на `/throttle`. Тогда process из лучшего становится худшим,
фиксированная таблица продолжает слать туда трафик по устаревшим данным,
а адаптивные политики должны это заметить. Это и есть настоящая проверка
того, что заявлено в названии статьи.

## Асимметричная деградация: главный положительный результат

В середине прогона процессный воркер теряет три четверти ёмкости
(остаётся 1 место из 4). В отличие от замедления общей зависимости, это
меняет относительный порядок воркеров, поэтому оптимальный выбор
действительно смещается.

| политика | до: avg / SLO | после: avg / SLO | рост |
|---|---|---|---|
| least_conn | 241.6 / 10.2% | 347.9 / 27.6% | +44% |
| least_work (фикс. таблица) | 247.5 / 9.4% | 527.5 / 25.7% | +113% |
| adaptive_work | 254.1 / 7.8% | 438.9 / 20.6% | +73% |
| online_model | 252.2 / 8.8% | 343.4 / 23.1% | +36% |

Статистика (бутстреп, вторая фаза):
- online_model против least_work: **-86 мс, ДИ [-137; -37] — значимо**
- least_conn против least_work: **-85 мс, ДИ [-135; -38] — значимо**
- online_model против least_conn по SLO: -2.6 п.п., ДИ [-7.0; +1.6] — **не значимо**

**Вывод для статьи.** Ценность адаптивной маршрутизации не в том, что она
точнее выбирает обработчик, а в том, что она не устаревает. Предвычисленная
таблица стоимостей — самый опасный вариант при изменении условий: задержка
выросла вдвое против +44% у простейшей балансировки. Политики, обновляющие
представление о системе, этого не допускают. При этом обучаемая модель не
даёт значимого преимущества перед least-connections — её ценность
проявляется только в сравнении со статическими подходами.

## Устранение двух методологических дефектов (выполнено)

Были исправлены две вещи, портившие модель с самого начала:

1. **Смещение обучения.** Модель училась на данных случайной политики,
   то есть на состояниях, которых при её собственной работе не бывает.
   Добавлена `ExploringPolicy`: данные собираются под управлением рабочей
   политики (least_work) с примесью случайного выбора в 35% решений —
   состояния реалистичные, покрытие вариантов сохранено.

2. **Слепота к настоящему.** Модель знала длину и вес очереди, но не
   знала фактическую скорость ответа воркера сейчас. Добавлен признак
   `recent_latency` — скользящее среднее наблюдаемых задержек
   (`QueueTracker.observe_latency`).

**Результат обучения на исправленных данных:**

| модель | MAE, мс |
|---|---|
| среднее по паре эндпоинт-воркер | 131.9 |
| линейная регрессия | **79.6** |
| нейросеть | 80.9 |

Точность выросла почти вдвое (было 137 мс), но **нейросеть стала хуже
линейной регрессии**. Объяснение: случайная политика загоняла систему в
экстремальные состояния, где зависимость нелинейна, и сеть эту
нелинейность ловила. В реалистичных состояниях зависимость почти
линейна, и сложная модель избыточна.

Это важный вывод для статьи: **нелинейность, ради которой нужна
нейросеть, существует только в нереалистичных режимах работы.**

## НОВАЯ ПОСТАНОВКА (реализуется сейчас, 18.09.2026)

### Диагноз старой постановки

Задача была слишком простой для машинного обучения. Шесть маршрутов с
фиксированной стоимостью каждый — это задача из теории очередей с точным
формульным решением. Выучивать нечего, поэтому арифметика по таблице
неизбежно побеждала, а модель лишь приближала то же самое с шумом. Это
было следствием искусственного упрощения, а не свойством задачи.

### Что изменено

**Стоимость запроса определяется его параметром, а не маршрутом.** Клиент
передаёт `limit`, `size` или `days`; прокси видит это значение в строке
запроса, не заглядывая в бизнес-логику. Замеренный разброс внутри одного
маршрута:

| запрос | полное время | из них CPU |
|---|---|---|
| `/api/search?limit=10` | 10 мс | 4 мс |
| `/api/search?limit=600` | 658 мс | 405 мс |
| `/api/report?days=8` | 13 мс | 6 мс |
| `/api/report?days=75` | 926 мс | 616 мс |

Разброс 65-70 раз внутри одного маршрута. Следствия:

- любая таблица «маршрут → стоимость» заведомо неверна для отдельного
  запроса;
- оптимальный движок меняется внутри маршрута: `search?limit=10` это
  лёгкий I/O (место в асинхронном движке), `search?limit=600` это 405 мс
  вычислений, которые в event loop блокируют всех соседей;
- экспертное правило по маршруту физически не может развести эти случаи.

Показатели степени различаются по маршрутам: для выборок из базы
зависимость линейная, для обработки изображения и агрегации за период —
квадратичная. Поэтому правило «умножить на параметр», которое инженер
пишет руками, верно не везде.

Значения параметра в трафике непрерывны (логравномерное распределение со
смещением к малым значениям), а не выбираются из известного списка:
оценка стоимости обязана обобщать на не встречавшиеся значения.

### Измеренная асимметрия движков (профилирование)

Для каждой пары «запрос, движок» измеряются две величины: собственное
время выполнения и суммарная задержка, причинённая лёгким обращениям,
которые шли на тот же движок параллельно.

| запрос | sync своё / ущерб | async своё / ущерб |
|---|---|---|
| `/api/auth/verify` | 129 / **18** | 123 / **121** |
| `/api/report?days=75` | 938 / **296** | 945 / **683** |
| `/api/image?size=2200` | 249 / 215 | 241 / 238 |
| `/api/feed?limit=400` | 493 / 17 | 491 / 46 |

Собственное время почти не зависит от движка. Расходятся движки в том,
сколько вреда запрос причиняет соседям: в потоковом сервере операции,
освобождающие GIL (хеширование, кодек JPEG, SQLite), выполняются
параллельно с обработкой других запросов, в event loop — нет.

Величина, которую имеет смысл складывать по очереди, — **занятость**
(собственное время + причинённая задержка), а не собственное время.

### Две разные величины о запросе, которые нельзя смешивать

Профилирование измеряет для каждой пары «запрос, движок» собственное
время выполнения и задержку, причинённую лёгким обращениям, которые шли
на тот же движок параллельно. Первая версия меры ущерба брала **сумму**
задержек — это оказалось методической ошибкой. Сумма измеряет потерю
пропускной способности, и по ней движки почти не различаются: в
потоковом сервере планировщик переключает потоки каждые несколько
миллисекунд, поэтому общее отобранное время примерно то же. Различие
движков — в **блокировке**: в потоке лёгкий запрос продвигается
порциями и завершается быстро, в event loop он ждёт чужое вычисление
целиком. Поэтому мера ущерба заменена на наибольшую задержку одного
обращения.

После замены картина стала физически осмысленной (мс):

| запрос | sync своё / блок | async своё / блок |
|---|---|---|
| `/api/auth/verify` | 128 / **9** | 124 / **123** |
| `/api/report?days=75` | 938 / **272** | 922 / **626** |
| `/api/report?days=45` | 325 / 81 | 323 / 212 |
| `/api/feed?limit=400` | 495 / 10 | 492 / 9 |
| `/api/search?limit=600` | 667 / 384 | 633 / 412 |

Собственное время от движка почти не зависит. Блокировка зависит сильно
там, где вычисление освобождает GIL (хеширование, кодек, SQLite), и
слабо там, где оно выполняется чистым Python-кодом (сортировка в
`/api/search`).

Отсюда две величины у каждой оценки стоимости: `cost` — полная цена
запроса, `blocking` — время, на которое движок недоступен остальным.
Очередь взвешивается блокировкой: ожидание внешнего сервиса на 500 мс
движок не занимает и веса в очереди почти не имеет.

### Точность оценки стоимости (главный численный результат)

Все оценки настроены на одной выборке из 384 замеров со значениями
параметра из рабочего распределения; проверка на 156 отложенных замерах
с не встречавшимися значениями. Медианная относительная ошибка:

| оценка | цена запроса | блокировка |
|---|---|---|
| среднее по маршруту | 80.3 % | 53.6 % |
| линейная поправка (показатель = 1) | 11.2 % | 35.0 % |
| степенной закон (показатель выучен) | 3.7 % | 11.1 % |
| нейронная сеть | 3.4 % | 12.6 % |

Разбивка по маршрутам показывает, где именно выигрывает обучение:
`/api/image/thumbnail` — 261 % / 55 % / 3.4 %, `/api/report/generate` —
251 % / 58 % / 7.0 %. Это маршруты с квадратичной зависимостью, для
которых экспертное правило «пропорционально параметру» неверно.
Контрольный случай `/api/auth/verify` (стоимость от параметра не
зависит) даёт 1.3 % у всех оценок — методика измеряет то, что задумано.

Выученные показатели степени против истинных: 1.87-1.95 против 2.00 для
квадратичных маршрутов, 0.93-1.02 против 1.00 для линейных. Показатель
модели не сообщался, он выведен из времён ответа.

### Схема эксперимента

Главный замер построен вокруг вопроса, который соответствует названию
работы буквально: **классификатор решает, безопасен ли запрос для event
loop**. Политика допускает запрос в асинхронный движок, только если
предсказанная блокировка не превышает порога; синхронный движок
принимает всё. Среди допустимых движков выбирается менее занятый.

Порог — не настроечная константа, а параметр компромисса: при нуле весь
трафик уходит в синхронный движок, при бесконечности политика
вырождается в балансировку по весу очереди. Набор порогов даёт кривую
«пропускная способность против хвоста задержек лёгких запросов», и
сравниваются кривые целиком, а не отдельные точки — это снимает произвол
в выборе рабочей точки.

Различаются политики единственным — источником оценки блокировки
(среднее по маршруту, линейная поправка, степенной закон, нейронная
сеть, точная таблица профилирования как верхняя граница).

Для отсчёта в замер включены `all_sync`, `all_async` (маршрутизации нет)
и `least_conn` (балансировка, не различающая запросы).

### Качество классификатора без шума нагрузки (`classifier_quality.py`)

Нагрузочный замер даёт итог, но его разброс между прогонами велик. Тот
же вопрос задан напрямую: разыгрывается 40 000 запросов из рабочего
распределения, для каждого известна истинная блокировка event loop (из
таблицы профилирования), и классификатор с данным порогом решает,
пускать ли запрос в асинхронный движок.

**При фиксированном пороге** — избыточная блокировка, попавшая в event
loop сверх порога, мс на тысячу запросов:

| 30 мс | 0 (но 19.6 % зря отклонено) | 27 | 33 | 35 |

| 250 мс | 3246 | 2680 | 59 | **14** |

**При равной доле трафика в асинхронном движке** (пороги подобраны так,
чтобы пропускная способность выравнялась по построению):

| доля | классификатор | блокировки, мс/1000 | самая тяжёлая пропущенная |
|---|---|---|---|
| 60 % | среднее по маршруту | 7340 | **421 мс** |
| 60 % | линейная поправка | 4745 | 11 мс |
| 60 % | обученная модель | 4749 | 18 мс |
| 70 % | среднее по маршруту | 13630 | **426 мс** |
| 70 % | линейная поправка | 6548 | 26 мс |
| 70 % | обученная модель | 6578 | 27 мс |
| 80 % | среднее по маршруту | 20054 | **622 мс** |
| 80 % | обученная модель | 10244 | 74 мс |

Решающий переход — от оценки по маршруту к оценке по запросу: вдвое
меньше блокировок при той же пропускной способности и в 8-16 раз
меньше самый тяжёлый прорвавшийся запрос. Именно он и создаёт хвост.

### Нагрузочный замер: Парето-граница (`benchmark_budget.py`)

Конкурентность 32, 500 запросов, 3 повтора на точку. Приведены режимы,
которых никто не превосходит сразу по обеим осям:

| режим | rps | лёгкие дольше 200 мс |
|---|---|---|
| весь трафик в асинхронный движок | 24.7 | 89.3 % |
| весь трафик в синхронный движок | 27.2 | 35.1 % |
| оценка по маршруту, порог 15 мс | 29.6 | 0.4 % |
| нейронная сеть, порог 15 мс | 31.1 | 3.1 % |
| нейронная сеть, порог 30 мс | 31.4 | 5.0 % |
| степенной закон, порог 30 мс | 35.1 | 6.9 % |
| линейная поправка, порог 60 мс | 38.7 | 14.4 % |
| least-connections | 44.1 | 44.4 % |

Два вывода:

1. **Любой режим с классификатором строго лучше обоих одиночных
   движков сразу по двум осям.** Степенной закон при пороге 30 мс:
   +42 % пропускной способности против «всё асинхронно» и в 13 раз
   меньше пострадавших лёгких запросов; +29 % и в 5 раз против «всё
   синхронно». Это прямое подтверждение гипотезы из названия работы.
2. **Оценка по запросу вытесняет оценку по маршруту почти отовсюду.**
   Из шести режимов «по маршруту» на границе остался один, самый
   консервативный. Остальные вытеснены: степенной закон при пороге
   30 мс даёт 35.1 rps при 6.9 %, оценка по маршруту в той же области —
   31.8 rps при 9.2 %, хуже по обеим осям.

Против least-connections — размен, а не победа: −20 % пропускной
способности за шестикратное снижение доли пострадавших лёгких запросов.
Так и следует написать, не выдавая это за чистый выигрыш.

Таблица прямого профилирования на Парето-границу не попала вовсе.
Называть её «верхней границей достижимого», как было в первой редакции,
неверно: она измеряет блокировку при одном сопутствующем запросе, а под
полной смешанной нагрузкой движок ведёт себя иначе. Формулировки в коде
исправлены.

### Сравнение при равной доле трафика (`benchmark_equal_share.py`)

Сравнивать классификаторы при одном пороге некорректно: порог означает
для разных оценок разное, и сравниваются разные рабочие режимы, а не
точность. Пороги подобраны так, чтобы доля трафика в асинхронном движке
была одинаковой.

Доля 70 %, 3 повтора по 500 запросов:

| классификатор | порог | rps | лёгкие p95 | лёгкие >200 мс |
|---|---|---|---|---|
| среднее по маршруту | 58 | 26.7 | 112 | 2.5 % |
| линейная поправка | 20 | 30.5 | 354 | 6.7 % |
| степенной закон | 15 | 29.9 | 182 | 4.6 % |
| нейронная сеть | 15 | **32.0** | **145** | **3.1 %** |

Перепроверка, 5 повторов по 600 запросов:

| классификатор | rps | лёгкие p95 | лёгкие >200 мс |
|---|---|---|---|
| линейная поправка | 33.7 ±6.2 | 415 | 7.5 % |
| степенной закон | 34.9 ±6.2 | 377 | 5.5 % |
| нейронная сеть | 35.4 ±5.7 | **158** | **2.6 %** |

Два независимых прогона дали одно направление и близкую величину:
обученная модель снижает хвост в 2.5 раза и долю пострадавших запросов
втрое при равной пропускной способности. Разброс по rps велик (±6), но
хвостовые показатели устойчивы.

### Противоречие между офлайн- и нагрузочным измерением, и его разрешение

Офлайн-анализ состава пропущенной в event loop работы при доле 70 %
показывает, что три оценки по запросу **неразличимы**:

| классификатор | сумма, мс/1000 | p90 | p99 | доля >50 мс |
|---|---|---|---|---|
| среднее по маршруту | 13630 | 28.4 | 251.9 | 4.78 % |
| линейная поправка | 6548 | 15.2 | 23.6 | 0 % |
| степенной закон | 6579 | 15.2 | 24.3 | 0 % |
| нейронная сеть | 6578 | 15.2 | 24.2 | 0 % |

То есть различие в нагрузочном замере возникает **не на допуске**.

Рабочая гипотеза: оценка применяется в двух ролях с разными
требованиями. Для допуска достаточно правильного **порядка** запросов
относительно порога — линейное правило монотонно по параметру и порядок
сохраняет. Для взвешивания очереди нужна верная **абсолютная величина**:
значения складываются между собой и сравниваются между движками, а
линейное правило ошибается на 11 % и систематически — на маршрутах с
квадратичной сложностью.

Гипотеза проверяется прямым экспериментом: две роли разведены по разным
источникам (`split_<допуск>_<вес>_<порог>`). Результат ожидается.

### Честный риск

Усложнение задачи не гарантирует победу обучаемой модели. Сильный
конкурент — `work_linear`, правило, которое инженер пишет за пять минут.
Оно верно для линейных маршрутов и занижает стоимость для квадратичных.
Если модель его не обойдёт значимо, это следует написать прямо.

## Итоговая линия статьи (если финальный замер не изменит картину)

Ценность адаптивной маршрутизации — не в точности выбора обработчика, а в
устойчивости к изменению условий. Три опорных факта:

1. Блокировка event loop измерена: лёгкий запрос деградирует с 25 мс до
   1643 мс, когда в асинхронный воркер попадает вычислительная задача.
2. Решает правильный признак, а не обучение: учёт веса очереди поднял
   балансировщик до 78 rps против 70 у обычного least-connections.
3. Предвычисленные правила устаревают: при потере воркером ёмкости
   фиксированная таблица дала +113% задержки против +36..44% у
   адаптивных подходов (значимо, ДИ не накрывает ноль).

Обучаемая модель значимого преимущества перед простой балансировкой не
показала — и это следует написать прямо, а не маскировать.

## Важные ограничения, о которых нельзя забывать

- Разброс между одинаковыми прогонами достигает 15%, поэтому любые
  выводы делаются только по нескольким повторам с оценкой разброса.
- Модель обучается на данных случайной политики, а работает в состояниях,
  которые создаёт сама. Это известный источник смещения, не устранён.
- Все замеры на одной машине (WSL2, 16 ядер), сеть и диск общие.
