## Что представляет собой проект сейчас

Шлюз принимает HTTP-запросы и выбирает, какому воркеру их отдать.
Воркеры (`workers/`): синхронный на потоках, асинхронный на event loop,
пул процессов. Нагрузка настоящая (`core/workload.py`): PBKDF2, сжатие
изображений, сортировка, SQLite, HTTP к отдельному stub-сервису — никаких
`sleep`. Шесть эндпоинтов с разными профилями.

Политики маршрутизации (`core/policies.py`): random, round-robin,
least-connections, least-expected-work, статическое правило, оракул,
обучаемая модель и гибрид.

## Ключевые результаты (проверены, с повторами и оценкой разброса)

1. **Без конкуренции воркеры почти неразличимы** (разница 1–3%). Вся
   разница рождается только под нагрузкой — из очередей и блокировок.

2. **Чистая обучаемая политика значимо проигрывает least-connections**:
   58.6 против 71.8 rps при конкурентности 16, 56.8 против 67.5 при 32.

3. **Причина установлена по данным**: модель отправляла 0% трафика на
   async-воркер, оставляя его простаивать, потому что для отдельного
   запроса он выглядит медленнее. Минимизация латентности запроса теряет
   пропускную способность системы.

4. **Гибрид (балансировка отсекает перегруженных, модель выбирает из
   оставшихся) сравнялся по пропускной способности и значимо улучшил
   SLO**: 17.8% нарушений против 22.9%, бутстреп-ДИ разницы
   [-9.4; -0.7] п.п. Улучшение p95 (-94 мс) незначимо, ДИ пересекает ноль.

5. **Статическое экспертное правило — худшее из всего** (-18% и -25% к
   least-connections). Маршрутизация по типу запроса без учёта загрузки
   вредна.

Итоговая формулировка: знание характера запроса не даёт выигрыша в
пропускной способности сверх простой балансировки по загрузке, но
встроенное в балансировку предсказание значимо снижает долю нарушений SLO.

## Эксперимент с изменением условий (выполнен, результат отрицательный)

Проверялось, даёт ли адаптивность преимущество, когда условия меняются:
в середине прогона внешний сервис замедлялся втрое.

| политика | до: avg / SLO | после: avg / SLO |
|---|---|---|
| least_conn | 246 / 9.4% | 337 / 16.1% |
| least_work | 260 / 7.4% | 351 / 27.0% |
| online_model | 251 / 7.4% | 365 / 22.9% |
| adaptive_work | 245 / 7.0% | 439 / 37.7% |

Адаптивные политики проиграли, least_conn выиграл. **Причина — ошибка в
постановке, а не свойство политик**: замедлялся внешний сервис, общий для
всех трёх воркеров, поэтому все подорожали одинаково и относительный
порядок между ними не изменился. Адаптироваться было не к чему, а
обновление оценок только добавляло шум.

**Следующий шаг: асимметричная деградация.** Нужно ухудшить один воркер
относительно других — например, сократить пул процессов с 4 до 1 через
семафор на `/throttle`. Тогда process из лучшего становится худшим,
фиксированная таблица продолжает слать туда трафик по устаревшим данным,
а адаптивные политики должны это заметить. Это и есть настоящая проверка
того, что заявлено в названии статьи.

## Асимметричная деградация: главный положительный результат

В середине прогона процессный воркер теряет три четверти ёмкости
(остаётся 1 место из 4). В отличие от замедления общей зависимости, это
меняет относительный порядок воркеров, поэтому оптимальный выбор
действительно смещается.

| политика | до: avg / SLO | после: avg / SLO | рост |
|---|---|---|---|
| least_conn | 241.6 / 10.2% | 347.9 / 27.6% | +44% |
| least_work (фикс. таблица) | 247.5 / 9.4% | 527.5 / 25.7% | +113% |
| adaptive_work | 254.1 / 7.8% | 438.9 / 20.6% | +73% |
| online_model | 252.2 / 8.8% | 343.4 / 23.1% | +36% |

Статистика (бутстреп, вторая фаза):
- online_model против least_work: **-86 мс, ДИ [-137; -37] — значимо**
- least_conn против least_work: **-85 мс, ДИ [-135; -38] — значимо**
- online_model против least_conn по SLO: -2.6 п.п., ДИ [-7.0; +1.6] — **не значимо**

**Вывод для статьи.** Ценность адаптивной маршрутизации не в том, что она
точнее выбирает обработчик, а в том, что она не устаревает. Предвычисленная
таблица стоимостей — самый опасный вариант при изменении условий: задержка
выросла вдвое против +44% у простейшей балансировки. Политики, обновляющие
представление о системе, этого не допускают. При этом обучаемая модель не
даёт значимого преимущества перед least-connections — её ценность
проявляется только в сравнении со статическими подходами.

## Устранение двух методологических дефектов (выполнено)

Были исправлены две вещи, портившие модель с самого начала:

1. **Смещение обучения.** Модель училась на данных случайной политики,
   то есть на состояниях, которых при её собственной работе не бывает.
   Добавлена `ExploringPolicy`: данные собираются под управлением рабочей
   политики (least_work) с примесью случайного выбора в 35% решений —
   состояния реалистичные, покрытие вариантов сохранено.

2. **Слепота к настоящему.** Модель знала длину и вес очереди, но не
   знала фактическую скорость ответа воркера сейчас. Добавлен признак
   `recent_latency` — скользящее среднее наблюдаемых задержек
   (`QueueTracker.observe_latency`).

**Результат обучения на исправленных данных:**

| модель | MAE, мс |
|---|---|
| среднее по паре эндпоинт-воркер | 131.9 |
| линейная регрессия | **79.6** |
| нейросеть | 80.9 |

Точность выросла почти вдвое (было 137 мс), но **нейросеть стала хуже
линейной регрессии**. Объяснение: случайная политика загоняла систему в
экстремальные состояния, где зависимость нелинейна, и сеть эту
нелинейность ловила. В реалистичных состояниях зависимость почти
линейна, и сложная модель избыточна.

Это важный вывод для статьи: **нелинейность, ради которой нужна
нейросеть, существует только в нереалистичных режимах работы.**

## ФИНАЛЬНЫЙ замер (конкурентность 32, 3 повтора)

| политика | rps | p95, мс | SLO% |
|---|---|---|---|
| least_work | **77.2 ± 3.6** | 770 | 17.6 |
| oracle (потолок) | 76.6 ± 9.8 | 621 | 14.0 |
| least_conn | 72.6 ± 4.6 | 977 | 18.6 |
| online_model | 71.2 ± 2.0 | 927 | **15.6** |
| model | 52.6 ± 3.1 | 1812 | 21.5 |

Переобучение на реалистичных данных **ухудшило** модель как политику
(-42% при конкурентности 16), хотя точность предсказания выросла вдвое.
Причина: данные собирались под least_work, которая редко выбирает async
(277 запросов из 1500), и модель переняла эту предвзятость. Устранение
одного смещения внесло другое — ловушка обучения на решениях учителя.

Проверка значимости по SLO: online_model против least_conn -2.7 п.п.,
ДИ [-6.8; +1.6] — **не значимо**. least_work против least_conn -0.9 п.п.,
ДИ [-5.0; +3.5] — не значимо.

**Вывод: в стационарном режиме обучаемый подход не даёт значимого
преимущества ни по одной метрике. Лучшая практическая политика —
least_work: арифметика по весу очереди, +6.5% к least-connections и
вровень с оракулом.**

Преимущество адаптивности проявляется только при изменении условий
(см. раздел про асимметричную деградацию): там online_model значимо
обошла фиксированную таблицу на 86 мс.

## ГЛАВНЫЙ ПЕРЕСМОТР ПОСТАНОВКИ (в работе)

Диагноз, к которому пришли после всех неудач: **задача была слишком
простой для машинного обучения**. Шесть эндпоинтов с фиксированной
стоимостью каждый — это задача из теории очередей, у которой есть точное
формульное решение («выбери минимальную ожидаемую работу»). Выучивать
нечего, поэтому арифметика неизбежно побеждает: она решает задачу точно,
а модель приближает то же самое с шумом.

**Исправление: стоимость запроса должна зависеть от его параметров, а не
только от эндпоинта.** В реальных API так и есть:
`/api/search?limit=5000` в сотни раз дороже, чем `limit=10`;
`/api/image/resize?size=2000` дороже `size=200` квадратично.

Что это меняет:
- таблица «эндпоинт → стоимость» становится принципиально неточной, так
  как усредняет запросы, отличающиеся в десятки раз;
- `least_work` начинает систематически ошибаться;
- модель, видящая параметры запроса (размер тела, значения query,
  заголовки — всё доступно прокси), может предсказать стоимость
  конкретного запроса;
- при нелинейной зависимости (квадрат стороны изображения) линейная
  регрессия тоже проигрывает, и появляется смысл в нейросети.

Это не подгонка под желаемый результат, а устранение нереалистичного
упрощения: прежняя постановка была искусственной.

План реализации:
1. `core/workload.py` — параметр запроса влияет на объём работы,
   разброс внутри эндпоинта в 10-50 раз, часть зависимостей нелинейна.
2. `experiments/load_generator.py` — генерация параметров с широким
   распределением.
3. `gateway.py` — передача параметра в признаки.
4. `core/predictor.py` — параметр как признак.
5. Baseline'ы остаются прежними: least_work усредняет по эндпоинту и
   должен проиграть.

## Итоговая линия статьи (если финальный замер не изменит картину)

Ценность адаптивной маршрутизации — не в точности выбора обработчика, а в
устойчивости к изменению условий. Три опорных факта:

1. Блокировка event loop измерена: лёгкий запрос деградирует с 25 мс до
   1643 мс, когда в асинхронный воркер попадает вычислительная задача.
2. Решает правильный признак, а не обучение: учёт веса очереди поднял
   балансировщик до 78 rps против 70 у обычного least-connections.
3. Предвычисленные правила устаревают: при потере воркером ёмкости
   фиксированная таблица дала +113% задержки против +36..44% у
   адаптивных подходов (значимо, ДИ не накрывает ноль).

Обучаемая модель значимого преимущества перед простой балансировкой не
показала — и это следует написать прямо, а не маскировать.

## Как запустить эксперимент

```bash
source venv/bin/activate
python workers/stub_service.py &      # порт 8100
python workers/sync_worker.py &       # 8201
python workers/async_worker.py &      # 8202
OMP_NUM_THREADS=1 python workers/process_worker.py &   # 8203

python experiments/build_cost_table.py       # таблица стоимостей
POLICY=random python gateway.py &            # 8300
python experiments/collect_dataset.py        # сбор обучающих данных
python experiments/train_predictor.py        # обучение модели
python experiments/benchmark_policies.py     # сравнение политик
python experiments/plot_policy_comparison.py # графики
```

Погасить всё: `ps aux | grep -E "[w]orkers/|[g]ateway.py" | awk '{print $2}' | xargs -r kill -9`

## Важные ограничения, о которых нельзя забывать

- Разброс между одинаковыми прогонами достигает 15%, поэтому любые
  выводы делаются только по нескольким повторам с оценкой разброса.
- Модель обучается на данных случайной политики, а работает в состояниях,
  которые создаёт сама. Это известный источник смещения, не устранён.
- Все замеры на одной машине (WSL2, 16 ядер), сеть и диск общие.
